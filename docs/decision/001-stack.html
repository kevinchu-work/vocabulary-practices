Decision 001 — Phase 1 Stack & Architecture

Accepted   Date: 2026-07-12  ·  Scope: Vocabulary-save & spelling-practice platform, Phase 1 proof-of-concept

Context

We want a platform to save vocabulary to a server and practise spelling it. Phase 1 is a single-user proof-of-concept: look a word up anywhere on macOS, see a definition with example sentences, save it to a server, and later practise spelling the saved words. Cost should be low or free. This record captures the stack and architecture choices and the alternatives considered.

Key constraint discovered

macOS's native Lookup popover (three-finger tap / Force Touch) is not extensible — Apple provides no supported way to add a custom vocabulary source or a "Save" button to it. We therefore reproduce the "select → look up → save" experience with our own trigger rather than hooking into the system panel.

Decisions

1. Explanation source — Merriam-Webster Learner's Dictionary

Chosen for clearer definitions and richer example sentences, which directly serve vocabulary and spelling practice. Free developer tier: 1,000 queries/day, non-commercial. The MW key stays server-side; responses are cached (see Decision 3) so the quota is rarely touched.

OptionVerdict
MW Learner's DictionaryChosen — simpler defs, most usage examples, reliable, free tier.
MW Collegiate DictionaryFallback — broader/advanced vocabulary, denser, fewer examples. Kept as a later add / fallback (separate free key).
Free Dictionary API (dictionaryapi.dev)Rejected — free but sparse/inconsistent examples; some words return nothing.
WordnikRejected for now — good aggregated data & audio, but historically slow key issuance.
Claude APIDeferred — highest quality & flexibility, small per-call cost; revisit if dictionary examples prove insufficient.

2. Front-end trigger — Native macOS menu-bar app + global hotkey

A SwiftUI MenuBarExtra app with a global hotkey. On the hotkey it captures the current selection (simulate ⌘C, read the pasteboard), calls our API, shows the definition in a popover, and offers a one-click Save. Closest feel to the native Lookup we can't extend.

OptionVerdict
Menu-bar app + hotkeyChosen — best UX, native feel, works in any app.
Shortcuts Quick ActionRejected — fastest to build but clunkier save flow via dialogs.
Raycast extensionRejected — nice UI but requires Raycast installed.

3. Backend + storage — Cloudflare Workers + Workers KV

One Worker serves the API, proxies/caches MW lookups, and serves the practice web page. Workers KV holds both the lookup cache and the saved vocabulary. Generous free tier, globally fast, single deploy.

OptionVerdict
Cloudflare Workers + KVChosen — API + KV in one deploy, generous free tier.
Deno Deploy + Deno KVRejected — strong TS DX, but no advantage over CF here.
Vercel + Upstash RedisRejected — only compelling if already on Vercel.

4. Practice UI — Simple web page served by the Worker

A plain HTML/JS page at /. Shows a saved word's definition/example with the word hidden; the user types it and gets scored. Easiest to build and demo; decoupled from the native app.

5. Auth & scope — Single-user static bearer token

Phase 1 is one user. The Mac app and practice page send a static bearer token; no accounts, no sign-up. Multi-user auth is explicitly out of scope until a later phase.

Consequences

Positive

  • Entirely free-tier for the PoC (CF free tier + MW non-commercial tier).
  • MW key never leaves the server; KV caching protects the daily quota.
  • Backend is independently testable via curl before any native UI exists.

Negative / risks

  • Menu-bar app needs a one-time Accessibility permission to read selected text; the grant can reset when an unsigned dev build is rebuilt.
  • MW's response JSON uses specialised markup tokens ({bc}, {it}, vis…) that require normalising.
  • KV is eventually consistent — acceptable for this app.
  • Single static token is not real auth — fine for a single-user PoC only.
